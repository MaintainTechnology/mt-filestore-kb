WHAT IT DOES

Three stages, one API: create a managed store, push files into it (uploaded or synced from Drive), then ask grounded questions against the indexed corpus. Every answer carries citations back to the source passages so the originating evidence can be verified.

01

What File Search is

Gemini File Search is Google's managed retrieval-augmented generation (RAG) service. There is no separate vector database to operate — Google hosts the store, the chunking, the embeddings, and the retrieval. This service is the operational layer on top that adds Drive ingestion, an API key gate, and grounded-answer parsing.

The retrieval pipeline collapses into three calls: create a store, upload (or sync) documents into it, then run generateContent with the file_search tool attached. The model decides which passages to retrieve from your store, composes an answer, and returns the chunks it leaned on as grounding metadata.

02

The pipeline

From an empty project to grounded answers in five steps. Steps three and four repeat as the corpus grows.

01
Create a store

POST /v1/stores creates a managed File Search store. The response carries the canonical name fileSearchStores/{id} used everywhere else.

02
Push documents in

Either upload directly (POST /v1/stores/{id}/upload, multipart) or sync a Drive folder (POST /v1/drive/sync). Uploads use Google's two-step resumable protocol under the hood, then poll the long-running operation until the document is chunked, embedded, and indexed.

03
Drive classification

For Drive ingestion the server walks the folder recursively, then classifies each file as export (Google Docs/Sheets/Slides → PDF/XLSX), download (regular file), or skip (audio, video, archive, executable, or anything over 100 MB).

04
Search

POST /v1/search runs generateContent with the file_search tool. Returns the answer plus deduped citations (title, page, snippet) extracted from groundingMetadata.

05
Iterate

Add or remove documents; queries pick up the new state on the next call. Stores can be inspected (GET /v1/stores/{id}/documents) and deleted (DELETE /v1/stores/{id}?force=true) safely.

03

04

Drive ingestion

Drive endpoints stay disabled until the server has a service-account credential. The setup is a one-time five-minute job in Google Cloud; after that, any Drive folder shared with that service account becomes ingestible.

  1. Open console.cloud.google.com and pick (or create) a project.
  2. Enable the Drive API for that project.
  3. IAM & Admin → Service Accounts → create one (e.g. mt-drive-access).
  4. On the new account → Keys → Add key → Create new key → JSON. Download.
  5. Either save the JSON as service-account.json at the repo root, or paste its single-line form into GOOGLE_SERVICE_ACCOUNT_JSON (recommended on Railway).
  6. Share the Drive folder you want to index with the service account's client_email (shown by GET /v1/drive/status). Viewer access is enough.

The server reads credentials once at boot. After changing the JSON or the env var, restart the process.

05

Quick start

From zero to a grounded answer, with curl. Substitute $KEY with your KB_API_KEY and the resulting store id where indicated.

curl -X POST https://<host>/v1/stores \
  -H "x-api-key: $KEY" -H "Content-Type: application/json" \
  -d '{ "displayName": "mt-knowledge-base" }'

curl -X POST https://<host>/v1/stores/<id>/upload \
  -H "x-api-key: $KEY" \
  -F "file=@./spec.pdf"

curl -X POST https://<host>/v1/search \
  -H "x-api-key: $KEY" -H "Content-Type: application/json" \
  -d '{ "store": "fileSearchStores/<id>", "query": "Summarise the rescue plan." }'

Prefer the browser? Open the console — same calls behind form controls, with grounded answers and citations rendered in place.
